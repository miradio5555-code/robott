# Автоматические проверки и резервная копия

## Проверки сайта

После отправки изменений в `main` GitHub проверяет JavaScript, переводы, подключённые файлы и версии. Изменения SQL дополнительно проверяются во временной базе. Результат появится в репозитории: **Actions → Проверки**.

## Ночная копия

Копия запускается каждую ночь: в 03:00 по Бишкеку и в 05:00 по Китаю. Архив зашифрован и хранится в GitHub Actions 30 дней.

### Что лежит в архиве

| Файл в архиве | Что это |
|---|---|
| `database.dump` | База: все таблицы с данными, функции, правила доступа (схема `public`) и пользователи с хешами паролей, входы, коды 2FA (схема `auth`). |
| `storage-buckets.sql` | Настройки всех хранилищ: имя, открытое или закрытое, лимит размера, разрешённые типы файлов. |
| `storage-policies.sql` | Правила доступа к файлам в хранилищах. |
| `storage/` | Все файлы из всех хранилищ (фото заказов, логотипы, QR, файлы поддержки и т. д.) и `manifest.json` со списком. |

### Что копия НЕ содержит (восстанавливается отдельно)

- **Секреты Edge Functions** (`GEMINI_API_KEY`, `TELEGRAM_BOT_TOKEN` и другие). Их Supabase не отдаёт. Храните их отдельно, например в менеджере паролей.
- **Код Edge Functions** лежит в папке `supabase/functions` репозитория. Копия его не включает: функции нужно заново создать в новом проекте.
- **Настройки входа** (Authentication): включённая регистрация по почте, Google, Face ID (Passkeys), адрес сайта (Site URL), письма. Заново включить вручную.
- **`config.js`**: в новом проекте адрес и публичный ключ другие, их нужно вписать в `config.js`.
- **Секреты GitHub** (четыре секрета для копии) и настройки GitHub Pages.
- **Webhook Telegram-бота** и любые ключи внешних сервисов, которые хранятся вне базы.
- **Realtime**: включение «живых» обновлений таблиц (см. шаг 6 ниже).
- **Сессии входа и журнал аудита** Supabase: после восстановления пользователям придётся войти заново.
- **Временные данные Supabase** (внутренние таблицы Storage с историей загрузок): создаются заново при загрузке файлов.

### Один раз добавьте секреты в GitHub

Откройте репозиторий → **Settings → Secrets and variables → Actions → New repository secret**. Добавьте четыре секрета:

| Имя секрета | Где взять значение |
|---|---|
| `SUPABASE_DB_URL` | Supabase → **Connect** → **Session pooler**. Строка подключения с паролем базы и портом 5432. |
| `SUPABASE_URL` | Адрес проекта Supabase, заканчивается на `.supabase.co`. |
| `SUPABASE_SERVICE_ROLE_KEY` | Supabase → **Settings → API Keys** → старый секретный ключ `service_role`. Он длинный, обычно начинается с `eyJ`. Это не публичный ключ `anon`. |
| `BACKUP_PASSWORD` | Придумайте длинный пароль и сохраните отдельно: без него архив нельзя открыть. |

Ключ `service_role` даёт полный доступ к базе и файлам. Добавляйте его только в GitHub Secrets, не в код и не в чат. Пароли и ключи в журнал запуска не выводятся.

### Как читать результат

Откройте **Actions → Копия базы**. Есть три исхода:

1. **Зелёная галочка** — копия создана, расшифрована и проверена (в сводке запуска виден размер). Архив лежит в **Artifacts** этого запуска.
2. **Красный, «КОПИРОВАНИЕ НЕ НАСТРОЕНО»** — не заданы секреты. Копии нет. Добавьте секреты и запустите вручную.
3. **Красный, «ОШИБКА КОПИРОВАНИЯ»** — секреты есть, но что-то сломалось (неверная строка базы, ключ, Supabase недоступен). Копии нет. Смотрите журнал шага.

Пока копирование не настроено, запуск каждую ночь будет красным. Это сделано нарочно: «не настроено» не должно выглядеть как «копия есть».

### Запустить первую копию вручную

После добавления секретов откройте **Actions → Копия базы → Run workflow**. Дождитесь зелёной галочки, затем скачайте архив из раздела **Artifacts**.

> **Не считайте копию надёжной, пока не сделали пробное восстановление** (ниже) хотя бы один раз на настоящем архиве. Раз в несколько месяцев повторяйте.

## Как восстановить

Восстанавливайте только в **новый пустой проект** Supabase. Не запускайте восстановление поверх рабочей базы.
Нужны Docker Desktop и Node. Команды ниже запускаются в Терминале; секреты в них подставляйте сами.

**1. Новый проект и архив.** Создайте новый проект на supabase.com. Положите скачанный архив `ula-ДАТА.tar.gz.gpg` в пустую папку (например, `~/restore`) и откройте её в Терминале.

**2. Расшифровать и распаковать** (команда спросит пароль `BACKUP_PASSWORD`):

```bash
docker run --rm -it -v "$PWD:/r" postgres:17 gpg -o /r/ula.tar.gz -d /r/ula-ДАТА.tar.gz.gpg
```

```bash
tar -xzf ula.tar.gz
```

**3. Хранилища.** В новом проекте: SQL Editor → вставьте содержимое `storage-buckets.sql` → Run.

**4. База.** Возьмите строку «Session pooler» нового проекта (порт 5432) и подставьте вместо `СТРОКА_НОВОЙ_БАЗЫ`. Сначала пользователи, потом данные приложения:

```bash
docker run --rm -v "$PWD:/r" postgres:17 sh -ec 'pg_restore -l /r/database.dump | grep -v "TABLE DATA auth schema_migrations" > /tmp/list; PGOPTIONS="-c session_replication_role=replica" pg_restore -d "СТРОКА_НОВОЙ_БАЗЫ" --no-owner --no-privileges -a -n auth -L /tmp/list /r/database.dump'
```

```bash
docker run --rm -v "$PWD:/r" postgres:17 env PGOPTIONS="-c session_replication_role=replica" pg_restore -d "СТРОКА_НОВОЙ_БАЗЫ" --no-owner --no-privileges --clean --if-exists -n public /r/database.dump
```

Предупреждения про роли или владельцев можно читать как «ничего страшного»; ошибки про `violates foreign key` или `does not exist` — нет, остановитесь и проверьте шаги.

**5. Правила доступа к файлам.** SQL Editor → вставьте содержимое `storage-policies.sql` → Run.

**6. Realtime.** SQL Editor → Run:

```sql
alter publication supabase_realtime add table public.support_messages, public.client_wallet, public.orders, public.clients, public.shipments, public.exchange_requests;
```

**7. Файлы.** Адрес и service_role ключ нового проекта (Settings → API Keys) подставьте вместо слов в скобках. Из папки проекта `robott`:

```bash
SUPABASE_URL="https://НОВЫЙ.supabase.co" SUPABASE_SERVICE_ROLE_KEY="КЛЮЧ" node scripts/restore_supabase_storage.mjs ~/restore/storage
```

**8. Настроить отдельно** (см. список «Что копия НЕ содержит»): Edge Functions и их секреты, Authentication, `config.js`, Telegram, GitHub Secrets.

**9. Проверить:** войти на сайте под своей учётной записью, открыть заказ с фото, отправить тестовое сообщение в поддержку.

## Проверка копии на компьютере (без настоящего Supabase)

```bash
bash tests/backup_selftest.sh
```

Скрипт создаёт две временные базы и поддельное хранилище, делает зашифрованную копию тем же скриптом, что и GitHub (`scripts/make_backup.sh`), восстанавливает её в пустую базу по шагам выше и сверяет данные и файлы. Он также проверяет исходы «не настроено» и «ошибка». Настоящую базу и настоящие ключи он не использует, поэтому проверка **не заменяет** пробное восстановление настоящего архива.
