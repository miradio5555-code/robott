# ULA Factory — учёт заказов из Китая

Система учёта заказов для закупок в Китае. Работает на GitHub Pages, данные хранятся в Supabase.
Языки интерфейса: русский, English, 中文.

## Как это работает

- **Ссылка для регистрации байеров**, без ограничения числа, подходит для групп: `https://miradio5555-code.github.io/robott/#/join`.
- **Личное приглашение** работает для одного человека 14 дней: «Байеры» → «Создать приглашение».
- **Байер регистрируется сам**: кнопка «Зарегистрироваться» на странице входа (имя, телефон, почта, пароль)
  или «Войти через Google». Ссылки-приглашения тоже работают. Байер сразу получает свой отдельный кабинет:
  свои заказы, клиенты, адрес склада. Другие байеры его данные не видят.
- **Админ** может открыть любой кабинет и посмотреть его (только чтение, менять нельзя),
  а также заблокировать байера.
- Номера заказов выдаются автоматически: `CN-000001`, `CN-000002`… Буквы меняются в настройках кабинета.
- Адрес склада в Китае вписывается в кабинете (блок «Склад в Китае» → «Изменить»)
  и копируется одной кнопкой вместе с контактами — для отправки клиенту.
- Для каждого заказа есть ссылка вида `https://miradio5555-code.github.io/robott/?order=токен`.
- Во вкладке ссылки байер может отключить ссылку или заменить её новой. Старая ссылка сразу перестаёт открывать заказ.
- По ссылке клиент видит только свой заказ и заполняет **данные для доставки**:
  ФИО, телефон, Telegram (необязательно), город, адрес или пункт выдачи.
- Если данные уже есть, клиент видит их и может нажать «Изменить».
  После статуса «Выдан клиенту» или «Отменён» менять нельзя.
- В кабинете:
  - в карточке заказа — блок «Данные клиента для доставки»;
  - на карточке в списке — город клиента или красная пометка «Нет адреса»;
  - вкладка «Клиенты» — поиск по имени и телефону, кнопка «Выгрузить в Excel (CSV)».
- Клиенту не показываются: поставщик, ссылка 1688, цена в ¥, курс и внутренний комментарий.

## Расчёты и валюты

В каждом заказе байер сам выбирает **валюту закупки** (в чём платит поставщику, например CNY или USD)
и **валюту для клиента** (в чём выставляет клиенту, например KGS, RUB, KZT). Валюты по умолчанию
задаются в настройках кабинета.

Валюта закупки — только **USD или CNY**.

- Товар (в валюте закупки) = количество × цена за единицу
- Товар в валюте клиента = товар × курс (сколько единиц валюты клиента за 1 единицу валюты закупки)
- Доставка (в валюте доставки, обычно USD) = вес × тариф за 1 кг (сумму можно вписать вручную)
- Доставка в валюте клиента = доставка × курс доставки
- **Себестоимость** = товар в валюте клиента + доставка в валюте клиента
- **Цена для клиента** — вписывает байер (или наценку в %, тогда цена посчитается сама)
- **Прибыль** = цена для клиента − себестоимость
- **Остаток** = цена для клиента − оплачено (если цена не указана — считается от себестоимости)

Валюта доставки и тариф за кг по умолчанию задаются в настройках кабинета.

Если валюты одинаковые, курс равен 1. В сводке на главной суммы считаются без отменённых заказов,
каждая валюта отдельно. Клиент по ссылке видит **только**: «К оплате», «Оплачено», «Осталось оплатить» — в своей валюте.
Цену у поставщика, доставку, курсы, тариф за кг, себестоимость, прибыль и WeChat поставщика клиент не видит.

## Умный помощник 💡

заказы без цены для клиента, без адреса доставки, без курса, в убытке, «застрявшие» (10+ дней без изменений),

## 📦 Партии (несколько заказов одним карго)

Раздел **«Партии»**. Как пользоваться:

1. «Новая партия» → название, карго, дата отправки, валюта доставки.
2. Укажите **тариф за 1 кг** или **сумму по счёту карго** (если указана сумма, тариф не используется).
   **Вес партии по весам карго** (необязательно): если пусто, берётся сумма весов заказов.
3. «Добавить заказы»: выберите заказы (не в другой партии, не отменённые и не выданные).
4. Внизу сразу видно, сколько получит каждый заказ. «Сохранить и разделить».

Как делится: стоимость партии (сумма по счёту или тариф × вес партии) распределяется между заказами **пропорционально их весу**
(`weight_kg` в заказе). Последний заказ получает остаток, поэтому сумма сходится до копейки. Каждому заказу записываются
доставка, тариф и валюта доставки, а курс берётся из «Моих курсов» (если для пары валют курса нет, остаётся прежний курс заказа и
показывается предупреждение). Себестоимость и прибыль заказа пересчитываются сами.

- Деление выполняет база (функция `shipment_recalc`, её проверяют автотесты); сайт показывает тот же расчёт заранее, пока вы вводите данные.
- Вес или статус заказа из партии поменяли, заказ удалили или отменили: партия делится заново автоматически.
- **Статус всей партии** меняется одной кнопкой, после этого можно по очереди «Сообщить клиентам».
- Заказ без веса доли не получает. Заказ, убранный из партии, сохраняет прежнюю стоимость доставки: поправьте её в заказе.
- В заказе, который лежит в партии, ручная правка доставки перезапишется при следующем пересчёте (в форме заказа есть предупреждение).

## 📊 Отчёт по прибыли

Раздел **«Отчёт»**: период (этот месяц / 3 / 12 месяцев / всё время), сверху — прибыль, выручка, себестоимость, сколько уже оплатили клиенты и сколько ещё должны.
Ниже три вида: **по месяцам** (с изменением к прошлому месяцу ▲▼), **по клиентам** (с долей в общей прибыли), **по товарам** (одинаковые названия объединяются).

- Считаются заказы с ценой для клиента, без отменённых. Месяц — по дате заказа. Прибыль = цена для клиента − себестоимость;
  наценка = прибыль / себестоимость (как в форме заказа). Сколько заказов без цены не вошло — написано внизу.
- Деньги в разных валютах не складываются: если есть несколько валют, появляется переключатель.
- Кнопка **«Выгрузить в Excel (CSV)»** сохраняет текущий вид и период (русские заголовки, число с десятичной запятой по языку интерфейса).
- Отчёт считается в браузере из уже загруженных заказов, ничего не отправляется.

## 💸 Долги и напоминания

Раздел **«Долги»** (в меню; туда же ведёт карточка «Долг клиентов» на главной).

- Долг = остаток по заказу (к оплате − оплачено) там, где указана **цена для клиента**. Заказы без цены и отменённые не считаются
  (иначе «к оплате» равнялось бы себестоимости, а её клиенту называть нельзя). Сколько таких заказов не вошло — написано внизу страницы.
- Заказы одного клиента объединяются (по телефону, иначе по имени). Суммы считаются отдельно по каждой валюте.
- **Просрочено** — 7 и больше дней с заказа или с последней оплаты. Выше в списке те, у кого товар уже прибыл или выдан, потом самые давние.
  Фильтр «Просроченные». Красная цифра у пункта меню «Долги» показывает, сколько клиентов просрочили оплату.
- Кнопка **«Напомнить об оплате»** открывает готовый текст (RU / EN / 中文): один заказ — с суммами и ссылкой на заказ, несколько — списком с итогом.
  Если долг старше 14 дней, добавляется строгая фраза. Дальше «WhatsApp», «Telegram» или «Копировать».
- Сайт сам ничего не отправляет. Когда нажали «WhatsApp», «Telegram» или «Копировать», у клиента появляется отметка «Напоминали: сегодня»
  (отметка хранится в этом браузере, не в базе).

## 🧮 Расчёт цены для клиента

Раздел **«Расчёт цены»** в меню. Порядок:

1. (по желанию) название товара и ссылка на него, например с 1688;
2. валюты (закупка USD/CNY и валюта клиента), количество, цена за 1 шт и **курс**;
3. вес (за всё или за 1 шт), валюта доставки, тариф за 1 кг, курс доставки;
4. наценка в % и округление цены вверх (до 10 / 50 / 100).

Считается так же, как в заказе: товар × курс + вес × тариф × курс доставки = себестоимость; цена для клиента = себестоимость × (1 + наценка).
Внизу готовый **ответ клиенту** (RU / EN / 中文) с кнопками «WhatsApp» и «Копировать». В нём только цена для клиента,
себестоимость и прибыль клиент не видит. Кнопка **«Создать заказ из расчёта»** открывает форму заказа, уже заполненную.

**Курсы.** Поля курса заполняются вашими сохранёнными курсами. Нет своего курса — подставляется рыночный (open.er-api.com) с пометкой.
Кнопка «Запомнить курс» сохраняет курс в кабинете (`workspaces.custom_rates`): он подставляется и в новые заказы.
Список сохранённых курсов, с возможностью удалить, внизу раздела («Мои курсы»). Наценку, округление и способ указания веса телефон запоминает.

## 🧭 Единый кабинет клиента (общая ссылка `?c=…`, файл 60)

Новой системы кабинетов нет: это та же общая ссылка из файлов 26/50/56, но понятнее.
- **Список заказов:** «В работе» и «Завершённые» (в том числе отменённые). У каждого заказа — товар, статус, **следующий шаг**, остаток к оплате в валюте заказа, ожидаемая доставка и трек. Если цена ещё не назначена, пишется «Цена пока не назначена», а не 0; если срока нет — «Срок пока не назван», дата не придумывается.

Зачесть предоплату в заказ может только байер; автоматической проверки оплаты по скриншоту нет. Неразобранная предоплата (без владельца) клиенту не показывается.
- **Доставка:** этап, трек, срок и адрес. Адрес по общей ссылке клиент может **указать только если у него ещё нет карточки** (`save_cabinet_client_info`); существующую карточку меняет только байер. Ссылка отдельного заказа работает как раньше (защита файла 56).
- **Одна главная кнопка:** «Связаться с байером» (когда нужно оплатить остатка или заказ прибыл), «Где посылка?» (в пути, оплаты нет) или сохранение адреса (форма). Кнопок без работающего процесса нет: «согласовать» и «реквизиты» не добавлены, пока таких процессов в программе нет.
- **Связь:** Telegram, WhatsApp и звонок открывают именно вашего байера. Байер сам указывает их в Настройках → «Связь с клиентами» (только владелец). Личный телефон из профиля клиентам не отдаётся. Секретные ссылки сторонним сервисам не передаются.
- **Telegram-уведомления:** показывается, включены ли они для **этого заказа**; подписка одного заказа не выдаётся за подписку на все. Включается по ссылке самого заказа.
- **Переход «заказ → общий кабинет»:** нет. Ссылка заказа не раскрывает общую ссылку; из общей ссылки заказ открывается внутри неё (сервер подтверждает доступ при каждом открытии, при отключении ссылки показывается «Ссылка не работает»).
- Без файла 60 кабинет работает по-старому: без срока, контакта и формы адреса (ничего не обещается и не выдумывается).

## Безопасность

- Ключ `anon` / `publishable` в `config.js` публичный, это нормально: доступ к данным закрыт правилами Row Level Security.
- Ключ `secret` / `service_role` вставлять в проект **нельзя**.
- Роли хранятся в таблице `profiles` (`admin` или `buyer`). Таблица `admins` больше не используется,
  её записи перенесены в `profiles`.
- Регистрация в Supabase должна быть **включена** (Authentication → Sign In / Providers → **Allow new users to sign up**).
  Каждый, кто зарегистрировался, получает **свой пустой кабинет** и не видит чужих данных.
  Лишних людей админ блокирует в разделе «Байеры».
- Supabase → Authentication → URL Configuration → **Site URL**: адрес сайта
  (`https://miradio5555-code.github.io/robott/`), чтобы ссылка из письма-подтверждения вела на сайт.
- Изоляция байеров проверяется самой базой (Row Level Security), а не только скрытием кнопок:
  даже прямой запрос к базе не вернёт и не изменит данные чужого кабинета.
- Рекомендуется добавить в пользовательское соглашение строку о том, что администратор платформы
  имеет доступ к данным для поддержки и безопасности (требование законов о персональных данных).
- Фото лежат в папке с непредсказуемыми именами. Загружать и удалять их может только байер своего кабинета.
- Перед изменениями в SQL запускайте проверки: `bash tests/run_db_tests.sh` (подробно в [DATABASE.md](DATABASE.md)).

### Как защищены данные клиентов

- Посетитель без входа **не может** читать или менять таблицу `clients` напрямую.
- Клиент работает только через две функции базы, и обе требуют секретный токен заказа из ссылки
  (32 случайных символа — подобрать невозможно):
  - `get_client_order(токен)` — показывает заказ и данные клиента, привязанного **именно к этому заказу**;
  - `save_client_info(токен, …)` — меняет **только** клиента этого заказа (или создаёт его, если ещё нет).
- Поиска клиентов по телефону для посетителей нет: нельзя ввести чужой номер и увидеть чужие данные.
- Формат телефона, длина полей и прочее проверяются дважды: на странице и в самой базе.
- Если ссылка попала к чужому человеку, он увидит этот один заказ. Ссылку отправляйте только самому клиенту.

## 🤖 Капча при входе и регистрации

Чтобы боты не создавали кабинеты и не подбирали пароли. Бесплатно, обычному человеку почти не видна.
1. Cloudflare → Turnstile → Add widget: домен `miradio5555-code.github.io` (потом ваш домен), режим «Managed». Cloudflare даст **Site key** (публичный) и **Secret key** (секретный).
2. **Site key** вписать в `config.js` → `TURNSTILE_SITE_KEY` и выложить файл на GitHub.
3. **Secret key** вставить в Supabase → Authentication → Attack Protection → Enable Captcha protection → Turnstile. Секретный ключ в `config.js` и вообще в код сайта вписывать нельзя.
Порядок важен: сначала п.2 (сайт научился присылать проверку), потом п.3. Если включить п.3 раньше, никто не сможет войти.

## 🧰 Инструменты байера

- **Объёмный вес** — меню «Ещё» → «Объёмный вес», или «📐 Посчитать по размерам» под полем веса в заказе и в «Расчёте цены». Длина × ширина × высота × коробки → объём (м³), объёмный вес (авиа ÷6000, экспресс ÷5000), плотность (кг/м³) и платный вес. «Вставить вес в заказ» сразу пересчитывает доставку.
- **Трек-номер** — поле «Трек-номер» в заказе. Клиент видит его на своей странице (кнопки «Копировать» и «Где посылка?» — сайт 17track), он же добавляется в сообщение «в пути» / «прибыл». По трек-номеру работает поиск.
- **PDF-счёт** — «⋯» на карточке → «PDF-счёт», или выбрать несколько заказов → «Счёт». Разные клиенты — разные страницы. Текст «Как оплатить» запоминается. В окне печати выбрать «Сохранить как PDF». Отменённые заказы в счёт не идут.
- **Этикетки с QR** — «⋯» → «Этикетка с QR», или выбрать заказы → «Этикетки». Размеры 58×40 мм (термопринтер), 100×70 мм, лист A4. «Мест» = сколько коробок (Место 1 из 3…). В QR — те же данные текстом, без ссылки на страницу клиента. QR рисует `js/qrcode.js` (MIT, Kazuhiko Arase), он загружается только при печати этикеток.
- **Расходы** — меню «Деньги» → «Расходы» (`js/expenses.js`, таблица `expenses`, файл `migration_23_tools.sql`). Прибыль с заказов − расходы = чистая прибыль; она же видна в «Аналитике». Видит и меняет только владелец кабинета, помощник — нет, админ только смотрит.

## ✅ Выданные заказы не мешают

На главном экране фильтр «В работе»: выданные клиенту и полностью оплаченные заказы туда не попадают — они во вкладке «Выданы» (внизу списка есть ссылка «Выданные и оплаченные: N»). Выданный, но не оплаченный заказ остаётся на главном экране, пока не закроют долг. Поиск, даты и подсказки помощника ищут по всем заказам. ## 📥 Загрузка старых заказов из Excel

Кнопка «Из Excel» на странице заказов (и меню «Ещё» → «Загрузить из Excel», и пустой кабинет). Файл `js/import.js`, без сторонних библиотек.
- Подходит .xlsx (Excel, Google Таблицы → Скачать → .xlsx) и .csv (UTF-8 или Windows-1251, разделитель «;», «,» или табуляция). Старый .xls — просим сохранить как .xlsx.
- Сайт сам находит строку заголовков (даже если сверху есть название таблицы) и угадывает колонки по словам на русском, английском и китайском. Байер проверяет и поправляет.
- Даты: числа Excel, «25.10.2026», «2026-10-25». Телефоны: «0555 12 34 56» → +996555123456. Суммы: «7 500 сом», «3 200,50». Статусы из текста («в пути», «выдан», «не оплачен»…), иначе — выбранный (по умолчанию «Выдан клиенту»).
- Строки без клиента пропускаются, уже существующие заказы (тот же клиент, товар, дата, сумма) не дублируются, до 5000 заказов за раз. Номер из файла — во внутренней заметке.
- Себестоимость → закупка в юанях по курсу байера; если курса нет — как доставка (с пометкой).
- Сразу после загрузки владелец может нажать «Отменить загрузку» — загруженные заказы удалятся.
- «Скачать образец таблицы» — готовый .xlsx с нужными колонками.

### 📷 Заказы с фото тетради
В том же окне — «📷 Фото тетради»: до 5 фото за раз, до 30 в день на человека (лимит в базе: `migration_24_photo_ai.sql`, функция `ai_photo_take`).

## 🗜 Сжатие фото
Все фото сжимаются в браузере до загрузки (`shrinkImage` в app.js): заказ — до 1280 px и ~250 КБ (WebP, если браузер умеет, иначе JPEG), плюс маленькая копия 360 px ~30 КБ (`…_t.jpg` рядом с `…_m.webp`) для карточек и списков. ## ✈ Клиент получает статусы в Telegram
На странице заказа клиента — блок «Уведомления в Telegram»: кнопка открывает бота со ссылкой `?start=o<токен заказа>`, клиент жмёт Start, возвращается — подключение проверяется само (`telegram-notify` → `client_connect`).
Когда байер меняет статус (один заказ, «Выбрать» → статус, статус партии, форма заказа), сайт зовёт `order_status` — бот пишет подписанным клиентам человеческим текстом (с трек-номером «в пути»/«прибыл» и ссылкой на заказ). Таблицы: `order_tg_subs` (подписки), `tg_updates` (все входящие Start — функция забирает их у Telegram и отмечает прочитанными, поэтому подключения не теряются при любом количестве). Файл `migration_25_client_telegram.sql`.

## 💱 Обмен сом → юань
Меню → «Деньги» → «Обмен сом → юань». Два курса, каждый сам по себе.
- **Курс ступенями по сумме в юанях**: например «от 1 000 ¥ — 12,60 сом», «от 10 000 ¥ — 12,40». До 10 ступеней; самая маленькая — минимальная сумма.
- **Мой курс для клиентов** (байер): включить «Показывать обмен клиентам», задать ступени и реквизиты для оплаты, «Сохранить курс». Ниже — **ссылка обмена** `?fx=…` (копировать / WhatsApp). Курс с калькулятором виден и на витрине, странице заказа, общей ссылке.
- **Клиент**: вводит, сколько юаней нужно → видит сумму в сомах → имя и телефон → видит реквизиты → оплачивает → «Загрузить скриншот оплаты».
- **Безопасность** (проверка 28.10.2026, файл 32): у всех таблиц правила строк (RLS); у анонимов нет прямого доступа ни к одной таблице — страницы клиентов работают только через функции по секретным ссылкам; у всех функций владельца задан `search_path`; закрытые хранилища (`fx-proofs`, `kyc`) видны только своим, у открытых нет списка файлов. В `index.html` — правило CSP (скрипты только с сайта и Cloudflare, данные только с Supabase, встроенные скрипты запрещены — поэтому код темы и «Загрузка…» вынесены в `js/head.js` и `js/boot.js`), `referrer: no-referrer` (секретные ссылки не утекают другим сайтам), защита от открытия в чужой рамке. Тест 26 проверяет это автоматически. В «Условиях использования» — раздел об обмене (платформа не сторона сделки, не держит деньги, байер отвечает за лицензию).
- **Сделка как P2P и споры** (файл 31): «Юани отправлены» байер ставит только со скриншотом перевода (клиент его видит); сделку закрывает клиент кнопкой «Юани получил ✅» с оценкой 1–5 — или она закрывается сама через 24 часа без спора. Байер не может сам поставить «выполнено» и не может отменить или удалить оплаченную заявку. Спор: клиент — если байер не подтвердил оплату за 2 часа, вышло обещанное время, юани не пришли (24 часа после отправки) или байер отменил оплаченную; байер — если деньги не пришли/скриншот поддельный. Пока спор открыт, байер статус не меняет; стороны переписываются и прикладывают фото. Администратор в «Обмен» → «Споры по обмену» видит обе стороны, скриншоты, переписку, число проигранных байером споров и решает «Прав клиент» (заявка снова «оплата подтверждена» — байер должен отправить) или «Прав продавец» (с занесением телефона клиента в чёрный список — байеры видят «⚠ Номер в чёрном списке»). Уведомления в Telegram: байеру — «получил», спор, сообщения, решение; администратору — споры и сообщения в них.
- **Проверка личности обменника** (файл 30): включить обмен можно только после проверки. Байер один раз загружает фото паспорта (лицевая сторона, по желанию — обратная), селфи с паспортом, ФИО и номер паспорта, ставит согласие. Администратору приходит сообщение в «Поддержку» (и в Telegram); в разделе «Обмен» у администратора — «Проверка обменников»: «Смотреть фото», «Проверен», «Отклонить» (с причиной), «Снять проверку» (обмен у байера выключается сам). Фото — в закрытом хранилище `kyc`: видят только сам байер и администратор, удалить может только администратор; после проверки подменить данные нельзя. Данные остаются и после удаления кабинета — чтобы при жалобе человека можно было найти. Клиент видит «✔ Продавец прошёл проверку личности».
- **Статус для клиента** (файл 29): страница `?xr=…` — «Ждём оплату» → «Скриншот получен — проверяем» → «Оплата подтверждена — ожидайте до 14:30 (осталось ≈ 25 мин)» → «Юани отправлены ✅», с сообщением байера; обновляется сама каждые 30 секунд. Клиент получает ссылку после заявки; на странице обмена видны «Мои заявки». Байер: «Оплата получена» → выбрать время (15 мин … 1 день) и сообщение → клиент сразу видит; «Юани отправлены»; кнопка WhatsApp отправляет клиенту ссылку на статус. В настройках курса — «Обычно отправляем юани в течение …» (клиент видит до оплаты).
- **Заявки** — вверху раздела: «Ждёт оплаты» / «Оплачено» (кнопка «Скриншот оплаты»), «Выполнено», «Отменить», звонок, WhatsApp. В меню — число активных заявок. В Telegram кабинета приходят «новая заявка» и «клиент оплатил» с фото скриншота.
- **Курс ULA для байеров** ставит админ в этом же разделе (тоже ступенями). Байеры с сомами / киргизским телефоном видят его и отправляют заявку админу в «Поддержку».
- Если курс обновлялся не сегодня — жёлтая надпись «уточните перед обменом». Лимиты: 5 заявок в час с одного телефона, 20 в час и 100 в день на кабинет. Скриншоты лежат в закрытом хранилище `fx-proofs`: загрузить можно только к своей свежей заявке, смотреть — только байер.
- База: файл 28; Telegram — функция `telegram-notify` (действия `exchange_notify`, `exchange_paid`).

## 🔗 Одна ссылка на все заказы клиента
В окне «Ссылка клиенту» внизу — блок «Одна ссылка на все заказы клиента»: «Создать общую ссылку» → скопируется адрес вида `?c=…`. Клиент открывает его и видит все свои заказы (в работе / завершённые), статусы, трек-номера, общий долг по валютам; нажал на заказ — та же подробная страница (фото, оплата, история), кнопка «Все заказы» возвращает к списку.
Клиент определяется постоянным номером в базе (`clients.id` = `orders.client_id`, файл 56), а не «9 цифрами или именем». Новый заказ присоединяется к существующему клиенту кабинета, только если телефон с кодом страны совпал полностью («+996 700 111 222» и «00996700111222» — один номер) и такой клиент ровно один. Заявки по ссылке никогда не присоединяются сами. «0700111222» без кода страны, совпадение последних 9 цифр или одинаковое имя клиентов не объединяют: такие пары показаны в «Клиенты → Совпадения», объединяет владелец вручную, по одной паре. Старые общие ссылки спорных клиентов отключены, пока вы не выпустите новую (см. DATABASE.md). Адрес доставки по общей ссылке только показывается; заполнять его клиент по-прежнему может по ссылке отдельного заказа. Эта ссылка видит и меняет только карточку, созданную по ней самой: чужая карточка (автосвязь по номеру, объединение) ей недоступна. Уведомления Telegram подключаются тоже на странице отдельного заказа.
«Отключить общую ссылку» — старая перестаёт работать, новая будет другой. Ссылки отдельных заказов не меняются. Таблица `client_cabinets`, функции `client_cabinet` (байер), `get_client_cabinet`, `get_cabinet_order` (клиент). Файл `migration_26_client_cabinet.sql`.

## 🔒 Цена для клиента и адрес заказа (файл 61)
- **Раньше (файлы 07/56/60):** у заказа без «цены для клиента» поле `total_som` подставляло себестоимость (юани × внутренний курс + доставка), `balance_som` = она минус оплата. Эти два поля уходили клиенту по общей ссылке и по ссылке заказа — клиент видел закупочную стоимость как «сумму» и «долг». Прибыль, курс, поставщик и заметки не уходили.
- **Теперь:** публичные ответы отдают `price_set`; `total_som`/`balance_som` — только при назначенной цене, иначе `null`; `paid_amount` (реальные платежи) всегда. «Долг» по валютам считается только по заказам с ценой. Внутренние столбцы и расчёты байера не менялись. Уведомление-напоминание об оплате и раньше не создавалось без цены (файл 58) — теперь это проверяется тестом.
- **Адрес:** `order_delivery` — одна запись на заказ (`proposed` — предложение клиента, `confirmed` — принят байером). Форма по ссылке заказа и по общей ссылке пишет только сюда: клиент, `client_id`, `client_card_ok`, предоплата и чужие карточки не меняются. Принятый адрес клиент по ссылке не перезаписывает. Байер видит адрес в карточке заказа и жмёт «Подтвердить адрес» / «Отклонить». Клиенту адрес показан как «отправлен на проверку», подтверждённым он назван только после принятия.
