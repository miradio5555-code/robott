# CRM: теги, заметки, предпочтения и история общения с клиентом — проект модели данных

Статус: **проект, миграция не создана.** Карточка клиента (`js/clientcard.js`) уже работает поверх существующих данных:
заказы, долг и просрочка, оплаты, статусы, контакты, быстрые действия. Ниже — что нужно для следующего шага и при каких условиях.

## 1. Что добавить и зачем

| Сущность | Зачем байеру | Пример |
|---|---|---|
| Теги клиента | быстрые списки и рассылки | «опт», «VIP», «медленно платит» |
| Заметка о клиенте | то, что нельзя забыть | «размеры обуви 42, не любит синий» |
| Предпочтения | подставлять в заказ | любимое карго, способ связи, язык |
| История общения | кто и когда писал | «звонил 12.11 — обещал оплатить в пятницу» |

## 2. Таблицы (файл `migration_67_…`, только по решению владельца)

```
client_tags        (workspace_id, id, name text 1..40, color text, unique (workspace_id, lower(name)))
client_tag_links   (client_id → clients on delete cascade, tag_id → client_tags on delete cascade, primary key (client_id, tag_id))
client_notes       (id, workspace_id, client_id → clients on delete cascade, body text 1..2000, pinned bool,
                    created_by uuid, created_at, updated_at)
client_prefs       (client_id primary key → clients on delete cascade, cargo text, contact_via text check in ('wa','tg','call'),
                    lang text check in ('ru','en','zh','vi'), updated_at)
client_contacts    (id, workspace_id, client_id → clients on delete cascade, channel text check in ('call','wa','tg','meet','other'),
                    direction text check in ('in','out'), summary text 1..500, happened_at timestamptz, created_by uuid)
```

Сообщения WhatsApp уже хранятся в таблицах файлов 52–55 — `client_contacts` их **не дублирует**: в карточке показывать ссылку
на диалог «Сообщения», а не копию текста.

## 3. Права доступа (RLS)

| Таблица | Читает | Добавляет / меняет | Удаляет | Клиент по ссылке |
|---|---|---|---|---|
| `client_tags`, `client_tag_links` | участники кабинета | владелец и помощник | владелец | **никогда** |
| `client_notes` | участники кабинета | автор и владелец | автор и владелец | **никогда** (внутренние заметки) |
| `client_prefs` | участники кабинета | владелец и помощник | — (через `clients`) | никогда |
| `client_contacts` | участники кабинета | владелец и помощник | владелец | никогда |
| Администратор платформы | видит только счётчики, не текст | — | — | — |

Ни одна из таблиц не попадает в `get_client_order`, `get_client_cabinet`, `client_order_json`. Это проверяет SQL-тест
(как в `tests/db_checks.sql`: клиент по ссылке не видит заметок).

## 4. Выгрузка и удаление данных

- **Выгрузка:** «Клиенты → Выгрузить в Excel» дополняется колонками «Теги» и «Заметки» (только для владельца); значения проходят `csvCell`
  (защита от формул Excel).
- **Удаление клиента:** всё каскадно (`on delete cascade`). Объединение клиентов (файл 56) переносит теги, заметки, историю
  на оставшуюся карточку — нужно дополнить функцию объединения, иначе данные пропадут.
- **Запрос клиента «удалите мои данные»:** удаляются заметки и история; заказы остаются (бухгалтерия), имя и телефон в заказах обезличиваются
  отдельной функцией — описать в политике конфиденциальности до запуска.
- Резервная копия (`BACKUP.md`) включает новые таблицы автоматически (копируется вся схема `public`).

## 5. Тесты, без которых миграцию не запускать

1. Изоляция кабинетов: чужой байер не видит и не меняет теги/заметки.
2. Клиент по ссылке и в кабинете клиента — ни одного поля из новых таблиц.
3. Помощник не удаляет чужие заметки; владелец — может.
4. Объединение клиентов сохраняет теги и заметки.
5. Повторный запуск файла; файл 66 поверх 67 останавливается.

## 6. Когда делать

Только если байеры просят именно это (тестируемая польза): например, ≥ 3 кабинетов ведут заметки о клиентах в комментариях
к заказам или в WhatsApp. До этого карточка клиента остаётся без новых таблиц.
