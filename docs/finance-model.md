# Деньги и маржа: как считается сейчас и что нужно для точного учёта

Документ к этапу 2.4 аудита. Код и база в этом этапе **не менялись**, кроме подписи «прибыль приблизительная»
в отчётах (`fin_approx`). Финансовые итоги задним числом не пересчитываются.

## 1. Текущая формула (файл `migration_07_client_price.sql`, не менялась до файла 66)

Все четыре поля — вычисляемые столбцы `orders` (`generated always as … stored`), в валюте клиента (`client_currency`):

| Поле | Формула | Кто видит |
|---|---|---|
| `cost_som` — себестоимость | `quantity × unit_price_cny × exchange_rate + delivery_cost × delivery_rate` | только кабинет |
| `total_som` — к оплате | `client_price`, если цена назначена, иначе себестоимость | кабинет; клиенту — только при `price_set` (файл 61) |
| `balance_som` — остаток | `total_som − paid_amount` | кабинет; клиенту — только при `price_set` |
| `profit_som` — прибыль | `client_price − cost_som`; **пусто**, пока цена не назначена | только кабинет |

Названия `_som` исторические: суммы в валюте клиента заказа, не обязательно в сомах.

Где прибыль используется: карточка заказа (`moneyHtml` в `app.js`), «Аналитика» (`js/analytics.js`), «Отчёт» (`js/report.js`),
«Расходы» → «Чистая прибыль» (`js/expenses.js`: прибыль по заказам − общие расходы), обзор администратора (`js/business.js`,
файл 51), ИИ-помощник администратора (сумма по валютам). Во всех местах учитываются только заказы с ценой
(`profit_som != null`) и без отмены.

## 2. Какие поля уже есть

| Что | Где | Замечание |
|---|---|---|
| Закупка: количество, цена, валюта (CNY/USD), курс | `orders` | курс вводится вручную, фиксируется в заказе |
| Доставка: вес, тариф, стоимость, валюта, курс | `orders` | `delivery_cost` вводит байер; фактический счёт карго не хранится отдельно |
| Цена для клиента, оплачено | `orders.client_price`, `orders.paid_amount` | `paid_amount` — итог, а не список платежей |
| История оплат | `order_status_history` (`event_type = 'payment'`, `paid_total`) | хранит **накопленный** итог; сумма платежа = разница |
| Баланс клиента (предоплата, возврат на баланс) | `client_wallet` (файл 50): `deposit`, `withdraw`, `order`, `return`, `fix` | `return` = вернуть оплату заказа **на баланс клиента**, а не деньги из кассы |
| Общие расходы кабинета | `expenses` (файл 23) | без привязки к заказу |
| Курсы | «Мои курсы» (файл 28), `fx_history` (файл 34) | история курсов обмена, не курс закупки |

## 3. Чего не хватает

| Пробел | Почему прибыль неточна | Пример |
|---|---|---|
| Возврат денег клиенту (наличными/переводом) | уменьшаем `paid_amount`, но прибыль не видит, что товар вернули и цену не получим | клиент вернул брак: прибыль остаётся как у проданного |
| Комиссии | перевод в Китай, комиссия Alipay/банка, комиссия площадки не входят в `cost_som` | 1–3 % от закупки теряются |
| Фактическая доставка | `delivery_cost` вводится как оценка; счёт карго за партию (`shipments`, файл 16) не распределяется по заказам в деньгах | вес уточнился — прибыль старая |
| Разница курса | курс закупки фиксирован в заказе; реальная стоимость юаней при оплате поставщику другая | купили юани дороже — прибыль завышена |
| Частичный возврат поставщиком | нет поля | поставщик вернул часть за недовложение |
| Корректировки | нет журнала: правка цены задним числом меняет прошлые отчёты без следа | отчёт за октябрь меняется в ноябре |

## 4. Как избежать двойного учёта

- **Одна сумма — одно место.** Комиссии заказа — в новой таблице корректировок заказа, а не одновременно в `delivery_cost` и в `expenses`.
- **Возврат на баланс ≠ возврат денег.** `client_wallet.return` деньги не выводит из кабинета; в прибыль не входит. Возврат денег клиенту — отдельный тип корректировки.
- **Партия карго.** Если счёт партии распределяется по заказам, `delivery_cost` этих заказов перестаёт вводиться вручную (или вводится только при отсутствии партии). Флаг источника обязателен.
- **Общие расходы** (`expenses`) остаются только для затрат без заказа (аренда, реклама). Подсказка в форме расхода.
- **Отчёты по периоду** берут корректировки по их дате, а не по дате заказа, иначе закрытый месяц меняется.

## 5. Предлагаемая модель (отдельный этап, новая миграция `migration_67_…` или позже)

```
order_adjustments
  id uuid pk, workspace_id uuid, order_id uuid → orders (on delete cascade)
  kind text check (kind in ('refund_client', 'fee', 'delivery_actual', 'fx_diff', 'supplier_refund', 'other'))
  amount numeric not null            -- со знаком: + увеличивает прибыль, − уменьшает
  currency text                      -- валюта клиента заказа (проверка в функции)
  happened_on date not null          -- для отчётов по периоду
  note text, created_by uuid, created_at timestamptz
RLS: участники кабинета читают; добавляют владелец и помощник; удаляет владелец. Клиенту — никогда (нет в публичных функциях).
```

- `profit_som` **не меняется** (обратная совместимость: старые отчёты, ИИ-помощник, обзор администратора).
- Новое представление или функция `order_profit_net(order)` = `profit_som + sum(adjustments)`; отчёты показывают обе цифры:
  «прибыль по ценам» и «прибыль с учётом возвратов и комиссий».
- Тесты: RLS (чужой кабинет, клиент по ссылке не видит), сумма по валютам, отчёт по дате корректировки, удаление заказа удаляет корректировки,
  повторный запуск файла, файл 66 поверх 67 останавливается.

## 6. Что сделано сейчас

Подпись под прибылью в «Аналитике», «Отчёте», «Расходах» и в карточке заказа: прибыль считается по введённым ценам
и доставке, без возвратов, комиссий и разницы курса. Цифры не меняются.

## 7. Что нужно решить владельцу

1. Нужен ли учёт возвратов и комиссий по заказу (таблица `order_adjustments`) — новая миграция.
2. Распределять ли счёт партии карго по заказам автоматически.
3. Закрывать ли месяц (запрет правок задним числом) — отдельная функция и миграция.
