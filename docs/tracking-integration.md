# Отслеживание посылок: что есть сейчас и как подключить перевозчика

Документ к этапу 2.5 аудита. Платный сервис и чужие ключи **не подключались**.

## 1. Как работает сейчас

| Часть | Где | Как |
|---|---|---|
| 10 этапов («Заявка принята» … «Получен клиентом») | `js/tracking.js`, файл 64 (`orders.track_stage`) | этап ставит байер вручную; без этапа он выводится из статуса |
| Дата отправки, срок в днях, город | файл 64 (`shipped_at`, `transit_days_min/max`, `ship_to`) | вводит байер |
| Обычный срок кабинета | файл 65 (`workspaces.default_transit_min/max`) | Настройки → «Срок доставки для клиентов» |
| Даты прибытия | файл 58 (`delivery_eta_from/to`) | блок «Сроки» в заказе; главнее срока в днях |
| «Срок увеличен» | `transit()` в `js/tracking.js` | только по сроку, который назвал байер, не по обычному сроку |
| Трек-номер | `orders.tracking_number` | вручную; кнопка «Где посылка» открывает 17track (сайт сам угадывает перевозчика) |
| История для клиента | `order_status_history`, событие `stage` с публичным комментарием (файл 64) | смена этапа уведомлений **не** отправляет |

Сделано в этом аудите (без внешнего API): клиент видит, **откуда срок** («указал байер» / «обычный срок карго, не данные
перевозчика»), **на сколько дней** прошёл названный срок и кнопку «Спросить байера» — она ведёт к блоку «Связаться»
и появляется, только если байер указал способ связи. Проверки — `tests/tracking_test.mjs`, группа 13.

## 2. Варианты подключения

| Вариант | Что даёт | Стоимость и ограничения | Риски |
|---|---|---|---|
| A. Агрегатор (17TRACK API, AfterShip, TrackingMore) | события сканирования по номеру, сотни перевозчиков, вебхуки | платно по числу номеров в месяц; бесплатные квоты малы; лимиты запросов (порядка единиц–десятков в секунду) | карго Китай → Бишкек часто ходит без сквозного номера: агрегатор знает только отрезок по Китаю |
| B. API конкретного карго | точные этапы именно вашей доставки (склад, граница, Бишкек) | зависит от карго; у многих API нет, есть только Excel или WeChat | нужен договор, формат у каждого свой |
| C. Импорт файла от карго | этапы партии из Excel | бесплатно; ложится на существующий импорт и «Партии» (файл 16) | вручную, раз в день |
| D. Оставить как есть | ручные этапы + 17track | бесплатно | точность зависит от байера |

Рекомендация: начать с **C** (файл от карго → этап у всех заказов партии), затем **A** только для заказов с настоящим
международным трек-номером. **B** — если карго предложит API.

## 3. Модель данных (отдельная миграция, когда будет выбран вариант)

```
tracking_events
  id uuid pk, workspace_id uuid, order_id uuid → orders (on delete cascade), shipment_id uuid null
  source text check (source in ('manual', 'carrier', 'aggregator', 'file'))
  code text            -- нормализованный этап: один из 10 этапов файла 64 или 'info'
  raw_status text      -- как прислал перевозчик (для разбора, клиенту не показывается)
  location text, happened_at timestamptz not null, received_at timestamptz default now()
  dedup_key text unique  -- source + номер + время + код: повтор вебхука не создаёт дубль
tracking_numbers
  order_id, number, carrier_code, last_checked_at, last_error, active
```

- **Права (RLS):** участники кабинета читают; пишет только серверная функция (service role). Клиент получает события
  через публичные функции (`get_client_order`, `client_order_json`), только поля `code`, `location`, `happened_at` — без `raw_status`
  и без цен.
- **Токены:** ключ агрегатора — только в секретах Supabase Edge Functions (`TRACKING_API_KEY`), никогда в `config.js` или в базе
  в открытом виде. Вебхук проверяет подпись (HMAC) и отвечает 401 без неё.
- **Лимиты:** опрос не чаще раза в 6–12 часов на номер, пачками; номера выданных заказов не опрашиваются; при 429 —
  откладываем по `Retry-After`.

## 4. Уведомления только о важном

- Клиенту сообщаем только о смене **одного из 10 этапов** вперёд (отправлен из Китая, прибыл, готов к выдаче), а не о каждом скане.
- Через существующую очередь (файл 57): дедупликация по `order_id + этап`, тихие часы, ручное включение владельцем.
- Откат этапа назад (ошибочный скан) клиенту не отправляется, только байеру.
- По умолчанию **выключено**: включает владелец (правило проекта — не отправлять уведомления автоматически без согласования).

## 5. Если API недоступен

- Страница клиента показывает последний известный этап и время обновления; ручной этап байера всегда главнее автоматического.
- Ошибка опроса пишется в `tracking_numbers.last_error` и в «пульс» (`job_beat`), клиенту не показывается.
- Если 3 суток нет данных — задача байеру в «Сегодня» («проверьте посылку вручную»), не клиенту.

## 6. План проверки

1. Юнит: нормализация статусов перевозчика → 10 этапов (таблица соответствий), дедупликация, откат этапа.
2. SQL (Docker): RLS, публичные функции не отдают `raw_status`, повторный вебхук не создаёт дубль, удаление заказа удаляет события.
3. Функция: подпись вебхука (401 без подписи), 429 и таймаут, секрет не попадает в ответ и журнал.
4. Стенд: страница клиента с событиями и без, на 375 px; уведомление уходит один раз.
5. Пилот: 1 кабинет, 1 карго, 2 недели, сравнение с ручными этапами.
