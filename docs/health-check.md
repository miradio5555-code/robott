# Работоспособность ULA Factory: что должно работать и что делать, если остановилось

Для владельца и того, кто дежурит. Все запросы ниже — **только чтение**, если не сказано иное.
Где сказано «только после копии» — сначала архив по `BACKUP.md`.

## 1. Что работает без браузера

| Задача | Как запускается | Период | Пульс (`job_heartbeats.job`) | Состояние сейчас |
|---|---|---|---|---|
| Отправка уведомлений клиентам из очереди | `pg_cron` `ula-order-notify` → Edge Function `order-notify-worker` (`supabase/notify_schedule.sql`) | 1 мин | `order_notify_worker` | **не включено** — сообщения копятся в очереди и не уходят |
| Задачи по срокам и постановка напоминаний | `pg_cron` `ula-deadlines` → `deadlines_scan()` (`supabase/deadlines_schedule.sql`) | 10 мин | `deadlines_scan` | **не включено** |
| Автозакрытие обмена через 24 часа | `pg_cron` `ula-fx-autoclose` → `fx_autoclose_job()` | 5 мин | `fx_autoclose` | **не включено** |
| Ночная копия базы и файлов | GitHub Actions `backup.yml` | раз в сутки | вкладка Actions, письмо при ошибке | по `BACKUP.md` |
| Проверки кода | GitHub Actions `checks.yml` | при каждой отправке | вкладка Actions | работает |

«Не включено» означает: расписание не создавалось. Включать только по шагу 6 `RELEASE_CHECKLIST.md` и после вашего «да».

## 2. Где смотреть пульс

- **В кабинете администратора:** раздел «Умный помощник» показывает строки «Серверная задача … работает / остановилась / не запускалась»
  (функция `jobs_status()`; «остановилась» = нет запуска дольше трёх периодов).
- **В SQL Editor:**

```sql
select job, last_run_at, last_ok_at, last_error, runs from public.job_heartbeats order by job;
select jobname, schedule, active from cron.job where jobname like 'ula-%';
select jobid, status, return_message, start_time from cron.job_run_details order by start_time desc limit 20;
```

## 3. Очередь уведомлений (файл 57)

Состояния сообщения (`order_notify_queue.status`):

| Состояние | Значит | Что видит владелец (Настройки → «Уведомления клиентам») |
|---|---|---|
| `pending` | в очереди, ждёт времени отправки | ожидает |
| `processing` | обработчик взял и отправляет | ожидает |
| `sent` | **Telegram принял сообщение** | отправлено |
| `failed` | не отправлено: 6 попыток, бот заблокирован, нет подписки, неясный ответ | ошибка + причина + «Повторить» |
| `skipped` | отправлять не нужно (уведомления выключены, клиент отписался) | — |

Важно: «отправлено» = провайдер (Telegram) принял. **Подтверждения, что клиент прочитал или получил, нет** — Telegram его не даёт.
Повторы: до `max_attempts` (по умолчанию 6) попыток с паузами; при неясном ответе (таймаут после отправки) — не больше одного повтора через 10 минут,
чтобы клиент не получил два одинаковых сообщения. Дубли защищены в базе: одно событие статуса и один получатель — одна задача (`unique (event_id, chat_id)`).
Журнал попыток — `order_notify_log`. Ручной повтор — `notify_retry(id)` (владелец, только для `failed`).

```sql
select status, count(*) from public.order_notify_queue group by status;
select id, status, attempts, last_error, next_attempt_at from public.order_notify_queue
 where status in ('pending','processing') order by next_attempt_at limit 20;
```

## 4. Очередь остановилась: что делать

1. Пульс `order_notify_worker` старый или пустой → расписание не включено или не срабатывает:
   `select * from cron.job where jobname = 'ula-order-notify';` — нет строки = не включено (это нормально, пока вы его не включили).
2. Строка есть, а в `cron.job_run_details` ошибки → смотреть `return_message`. Частое: неверный адрес проекта или секрет в Vault.
3. Пульс свежий, но `last_error` = `worker_error` → Edge Functions → `order-notify-worker` → Logs. Проверить секреты
   `TELEGRAM_BOT_TOKEN` и `NOTIFY_WORKER_SECRET` (не короче 32 символов). Ответ 503 `not_configured` / 401 `unauthorized` — секрет не совпадает.
4. Много `failed` с `bot_blocked` / `chat_not_found` — клиенты отписались; это не поломка.
5. Застряли в `processing` — когда истечёт блокировка (`locked_until`), обработчик сам вернёт их в очередь при следующем проходе.
6. Выключить отправку разом (безопасно, ничего не теряется): `select cron.unschedule('ula-order-notify');`
   Сообщения остаются в очереди. **Это изменение — только с вашего согласия.**

Удалять строки очереди или журнала, массово ставить `skipped` — **только после копии** и с вашего согласия.

## 5. Перед выпуском

1. `npm run release:check` → «ГОТОВО» (`RELEASE_CHECKLIST.md`, шаг 0).
2. Свежий архив и пробное восстановление (шаг 1).
3. Диагностика рабочей базы `scripts/diagnose_supabase_readonly.sql` (шаг 2) — какие файлы запущены.
4. Пульс и очередь (запросы выше) — нет ли зависших сообщений перед изменениями.
5. Edge Functions: после изменения кода функции — Deploy вручную (SQL-файлы функции не обновляют).

## 6. Только после копии базы

- запуск любого SQL-файла `migration_*.sql` в рабочей базе;
- включение расписаний (`notify_schedule.sql`, `deadlines_schedule.sql`);
- массовые изменения: объединение клиентов, распределение спорной предоплаты, удаление кабинетов и заказов;
- очистка очереди уведомлений и журналов.
