# База данных ULA Factory: как обслуживать

База — Supabase (Postgres). Всё её устройство описано в SQL-файлах в корне проекта.
Номер файла = его версия: `supabase_schema.sql` — это 0, `migration_07_…` — это 7 и так далее.

## Какие файлы уже запущены

В базе есть таблица `schema_migrations`. Каждый файл в конце сам ставит в ней отметку о себе.

Посмотреть: Supabase → SQL Editor → New query →

```sql
select version, name, applied_at from public.schema_migrations order by version;
```

Последнее **подтверждённое** состояние: файлы **0–49**. Про файл **50** пользователь сообщал, что запустил его, а файл **51** (бизнес-обзор администратора) добавлен в код позже. Их наличие в рабочей базе нужно проверить: запустите `scripts/diagnose_supabase_readonly.sql` (см. ниже). Файл 51 запускается только после 50: иначе он остановится с сообщением «СТОП: сначала запустите миграцию 50». Файл 50 после запуска 51 повторно не запускается (остановится сам). Файл **52** (клиент по постоянному номеру) подготовлен и проверен только во временной базе, в рабочую базу не применён. Файл **53** (очередь уведомлений клиентам) подготовлен и проверен только во временной базе, в рабочую не применён; он запускается только после 52. Файл **54** (сроки, задачи, напоминания) подготовлен и проверен только во временной базе, в рабочую не применён; он запускается только после 53. Файл **55** (ежедневная работа) подготовлен и проверен только во временной базе, в рабочую не применён; он запускается только после 54. Файл **56** (единый кабинет клиента) подготовлен, но **его проверки базы (`tests/cabinet_test.sh`) ещё не запускались** (Docker не отвечал) и в рабочую базу он не применён; запускается только после 55. Следующий номер нового файла — 57.

Вход по Face ID (Authentication → Passkeys) включается в панели Supabase, из SQL это не видно. Серверные функции (`supabase/functions/`) устанавливаются отдельно от SQL-файлов (см. ниже).

## Проверка рабочей базы на соответствие коду (только чтение)

Файл `scripts/diagnose_supabase_readonly.sql` ничего не меняет и не показывает данные клиентов, ключи и почты. Он сверяет реестр запущенных файлов, таблицы и функции, правила доступа, хранилища, Realtime и признаки настройки уведомлений.

1. Supabase → SQL Editor → New query.
2. Вставить весь файл → Run.
3. Скопировать получившуюся таблицу и отправить помощнику. Статус `ПРОБЛЕМА` — расхождение, `ПРОВЕРИТЬ` — похоже на «ещё не настроено», `ВРУЧНУЮ` — из SQL не видно, смотреть в панели.

| Секрет `NOTIFY_WORKER_SECRET` (не короче 32 символов) | Edge Functions → Secrets и Vault базы (одно и то же значение) | защита вызова обработчика |

| Вход по почте, Google, Site URL, капча, Passkeys | Authentication | регистрация и вход |

## Как определяется клиент (файл 56)

Раньше «один клиент» = последние 9 цифр телефона или, без телефона, имя. Это могло смешать разных людей (например, «+996 700 111 222» и «+7 700 111 222», два «Азиза» без телефона). Теперь клиент — это строка `clients` (её `id` лежит в `orders.client_id`), и к ней привязаны заказы, предоплата (`client_wallet.client_id`) и общая ссылка (`client_cabinets.client_id`). У каждого байера свои клиенты: один человек у двух байеров — две разные строки.

- Новый заказ присоединяется к клиенту только при полном совпадении телефона с кодом страны с ровно одним клиентом кабинета. Заявки по ссылке сами не присоединяются. Иначе создаётся новый клиент без карточки. В «Клиентах» он скрыт кнопкой, но находится поиском, его имя, телефон и Telegram байер может исправить кнопкой «Исправить» (после исправления телефона ключ поиска совпадений следует за ним).
- Последние 9 цифр, имя, номер без кода страны ничего не объединяют, а попадают в «Клиенты → Совпадения». Объединяет только владелец, по одной паре; строки выписки не удаляются, всё пишется в `client_merge_log`.
- Старые данные переносятся при запуске файла 56 один раз: однозначные связи переносятся, спорные нет. Спорная предоплата остаётся «неразобранной» (не входит ни в чей баланс, видна в «Совпадения»); спорная общая ссылка отключается (клиент увидит «ссылка не найдена»). Причины лежат в `client_link_review`. Суммы по кабинетам и валютам до и после сверяются, при расхождении весь файл откатывается («СТОП»). Таблица сверки: `client_migration_audit`.
- **Ссылка отдельного заказа и чужая карточка.** Совпадение телефона не даёт ссылке заказа доступа к карточке (адрес, контакты). Поле `orders.client_card_ok` = «карточку создала форма по ссылке ЭТОГО заказа»: при переносе оно ставится только заказам, у которых клиент уже был; автосвязь по номеру, заявки и ручное объединение его не ставят (объединение сбрасывает). Страница заказа (`get_client_order`) показывает карточку и форма адреса (`save_client_info`) меняет её только при `client_card_ok = true`; иначе форма создаёт для заказа новую карточку и не читает и не перезаписывает чужую. Если у клиента карточка на объединённом заказе была видна по ссылке заказа, после объединения её уже не будет видно: клиент увидит форму адреса.
- **Спорные деньги** распределяются только владельцем, по одной операции (`client_wallet_assign_rows`): итоги по валютам до и после сверяются, повторно распределить операцию нельзя, деньги, оплатившие заказ, достаются только клиенту этого заказа, баланс не уходит в минус, каждое решение пишется в `client_wallet_assign_log`. Неразобранные суммы видны в «Совпадения», в сверке (`wallet_reconcile`: всего = у клиентов + неразобрано) и строкой над списком должников.
- **Старый сайт** (открытая вкладка, установленное приложение) после файла 56: `wallet_add` по-старому отклоняется ошибкой `app_update_required` (ничего не сохраняется), `wallet_order`/`wallet_undo` работают по клиенту заказа, `wallet_totals` отдаёт поле `ckey` вида `client:<id>`, которое не совпадает ни с одним старым ключом. Старая вкладка покажет общую ошибку и пустые балансы по клиентам до обновления страницы.
- Ссылки отдельных заказов (`?order=…`) продолжают работать.

**Что нужно перед запуском файла 56 в рабочей базе:**
1. Файл 50 запущен (проверяется самим файлом). Файл 51 для этого не нужен.
2. Выполнена диагностика `scripts/diagnose_supabase_readonly.sql` (какие файлы реально запущены) и оценка переноса `scripts/preview_migration_56_readonly.sql` (сколько групп спорных, сколько ссылок отключится, суммы спорных денег по кабинетам и валютам, сколько заказов без надёжной связи; только чтение, личных данных не выводит).
3. Сделана настоящая резервная копия и проверено пробное восстановление в отдельный проект (BACKUP.md).
4. Запускать файл целиком одним запросом в SQL Editor (файл сам открывает транзакцию, при любой ошибке откатывается всё), затем сразу обновить сайт (js/wallet.js, js/debts.js, js/clientlinks.js и др.): старый сайт вызывает `wallet_add` по-старому и получит ошибку, а новый сайт без файла 56 не покажет кнопок баланса.
5. После запуска: диагностика покажет число неразобранных связей; владелец разбирает их в «Клиенты → Совпадения».

Проверки на временной базе (входят в `bash tests/run_db_tests.sh`): `tests/client_identity_test.sh` (17 групп), `tests/client_identity_rollback_test.sh` (нарочная ошибка в четырёх местах файла: вся база, функции и отметки миграций в точности как до запуска), `tests/preview_56_test.sh` (оценка совпадает с тем, что файл потом сделал).

## Уведомления клиентам о статусах (файл 57)

**Как работает.** Смена статуса заказа и сообщение в очереди (`order_notify_queue`) сохраняются одной транзакцией (триггер `orders_notify_enqueue`): откатилась смена — события нет, закрыли сайт — сообщение не потеряно. Одна строка очереди — одно сообщение одному подписчику заказа (`order_tg_subs`). Событие создаётся только при настоящей смене статуса: тот же статус повторно и статус «new» ничего не создают, каждый настоящий переход (например «в пути → прибыл → в пути») — отдельное событие. Для старой истории событий нет: после установки очередь пуста. Отправляет Edge Function `order-notify-worker` по расписанию (раз в минуту), сайт не нужен.

**Повторы и параллельность.** Задачи берутся пачкой через `FOR UPDATE SKIP LOCKED` (`notify_claim`) с арендой на 2 минуты: два обработчика одну задачу не возьмут; если обработчик пропал, задача возвращается. Временная ошибка (5xx, 429, нет сети) → повтор через 1, 2, 4… минут (не дольше часа; 429 учитывает `retry_after` Telegram), всего не больше 6 попыток, затем «ошибка». Постоянная ошибка (400, 401, 404) → сразу «ошибка» без повторов. 403 (клиент заблокировал бота) → подписка снимается, строка «не отправлено». Сообщения одного заказа и чата уходят по порядку. Результат и безопасное описание причины (без токена бота и ссылок) хранятся в строке; все действия — в `order_notify_log`.

**Получатели.** Перед отправкой (и повторно непосредственно перед запросом к Telegram) проверяется: подписка существует, не создавалась заново после события, ссылка заказа не отключена (замена или отключение ссылки и так удаляют подписки, файл 25). В сообщении только то, что клиент видит на своей странице заказа: название и номер заказа, статус, трек-номер, ссылка заказа, название кабинета; закупочных цен, прибыли, заметок и данных других клиентов в задаче нет (проверено тестом по точному списку полей).

**Гарантии и ограничения.**
- Сообщение не теряется при закрытии сайта и сбое сервера: оно хранится в базе, пока не отправлено или не станет видимой «ошибкой».
- Telegram не даёт ключа идемпотентности, поэтому **абсолютной гарантии «ровно одно сообщение» нет**. Если Telegram принял сообщение, а ответ потерялся (таймаут), исход неизвестен: делается ОДИН повтор не раньше чем через 10 минут (возможен дубль), после второго неизвестного исхода строка получает «ошибка: исход неизвестен», автоматических попыток больше нет. Так же поступаем, если обработчик пропал во время отправки.
- Повторить после ошибки вручную может только владелец кабинета (Настройки → «Уведомления клиентам» → «Открыть журнал»). Строка возвращается в ту же очередь, действие пишется в историю; если прошлое сообщение всё же дошло, клиент получит его дважды (окно подтверждения об этом предупреждает).
- Доставка зависит от включённого расписания. Пока оно не включено, сообщения копятся, но не уходят.

**Старые вкладки и приложение.** Новый сайт сам ничего не отправляет, если очередь установлена (признак `notify_queue_enabled()`); без файла 57 он работает по-старому (запасной путь). Старая вкладка зовёт `telegram-notify` (`order_status`): новая версия функции при наличии очереди ничего не отправляет, поэтому дублей нет; если проверка очереди не удалась, она тоже не отправляет (лучше пропустить, чем продублировать).

**Порядок выпуска (важно).**
1. Задеплоить новую `telegram-notify` и `order-notify-worker` (`supabase functions deploy order-notify-worker --no-verify-jwt`), задать секреты `TELEGRAM_BOT_TOKEN`, `NOTIFY_WORKER_SECRET`. До файла 57 новая `telegram-notify` ведёт себя как прежняя.
2. Запустить `migration_56_client_identity.sql` (после диагностики, оценки переноса, настоящей копии и пробного восстановления), затем `migration_57_notify_queue.sql` одним запросом (при ошибке откатывается всё). Файл 57 без 52 не запустится, а запущенный 53 не даст потом запустить 52.
3. Включить расписание: `supabase/notify_schedule.sql`. Проверка: `select * from cron.job_run_details …` (запросы в конце файла) и строка 94 диагностики.
4. Только потом публиковать новый сайт (он показывает «Уведомления клиентам» в настройках).

Проверка на временной базе: `bash tests/notify_queue_test.sh` (входит в `bash tests/run_db_tests.sh`): сохранение события вместе со статусом, откат, повтор статуса, повторные переходы, временная и постоянная ошибки, потерянный ответ, параллельные исполнители, порядок, отзыв доступа, старый вызов, изоляция кабинетов, закрытые данные. Тесты используют поддельные базу доставки и Telegram, настоящие сообщения не отправляются.

## Сроки, задачи и напоминания (файл 58)

**Сроки.** У заказа появились `payment_due_at` (срок оплаты) и `delivery_eta_from` / `delivery_eta_to` (ожидаемый интервал доставки). Время хранится в UTC; вводится и показывается в часовом поясе кабинета (`workspaces.time_zone`, по умолчанию Asia/Bishkek — владелец меняет в Настройках) с названием пояса. У старых заказов сроков нет и не придумывается: **заказ без срока никогда не считается просроченным** (ни по дате создания, ни по дате платежа). «Просрочено» — строго позже срока (ровно в момент срока ещё нет); интервал доставки заканчивается в конце последнего дня по времени кабинета. Любое изменение срока и приостановки пишется в `order_deadline_history` (кто и когда).

**Задачи** (`order_tasks`) показываются в «Умном помощнике» и в карточке заказа владельцу и помощникам кабинета: истёк срок оплаты (долг остался), срок доставки приближается (за 2 суток) / прошёл, не хватает данных для следующего этапа (нет цены при «ожидает оплаты», нет веса на складе в Китае, нет трек-номера в пути). У задачи есть причина, заказ и действие. Дублей нет: ключ «заказ + вид + цикл срока». Оплата, отмена, смена этапа или перенос срока закрывают задачу сразу (триггер), перенос срока открывает новый цикл. Задачу можно отложить на 3 дня. Просрочка доставки создаёт ТОЛЬКО внутреннюю задачу: клиенту ничего не пишется и статус сам не меняется.

**Напоминания клиенту об оплате — по умолчанию ВЫКЛЮЧЕНЫ** (нет строки в `ws_reminder_settings`). Владелец включает их в Настройки → «Напоминания об оплате», подтвердив показанные правила: часы отправки (по времени кабинета, по умолчанию 9–20), пауза после срока (24 ч), интервал между напоминаниями (72 ч), максимум на заказ (3) и в сутки по кабинету (50). Идут через очередь файла 57 (`kind = payment_reminder`) и подписки Telegram, новых каналов и отдельной системы доставки нет. Перед фактической отправкой всё проверяется заново: автоматизация включена, заказ не приостановлен и не отменён, срок не перенесён, долг не погашен (устаревшее напоминание не уходит), подписка и ссылка действуют, суточный лимит; вне часов отправки сообщение переносится на ближайшее окно (попытка не тратится). Приостановить напоминания по заказу (например при споре о товаре) может любой участник кабинета кнопкой в карточке заказа. Включать и менять правила — только владелец (журнал `ws_reminder_log`).

**Серверные задачи без браузера.** `deadlines_scan()` (задачи + постановка напоминаний, каждые 10 мин) и `fx_autoclose_job()` (автозакрытие обмена, каждые 5 мин) запускаются расписанием pg_cron напрямую в базе: `supabase/deadlines_schedule.sql` — **НЕ включено, пока вы не выполните файл**. Контроль сроков и доставка сообщений разделены: доставку делает `order-notify-worker` (расписание из файла `supabase/notify_schedule.sql`). Каждый запуск пишет «пульс» (`job_heartbeats`, период × 3 без запуска = «остановилась»); администратор видит в «Помощнике» (вкладка «Байеры»): не запускалась / работает / остановилась / ошибка. Описание ошибки в пульс не пишется (только код).

**Обмен: автозакрытие.** Правила прежние (файл 31): «юани отправлены» без ответа клиента 24 часа и без открытого спора → «выполнено». Раньше его лениво запускал браузер, теперь — сервер (`fx_autoclose_all`: строки, которые в этот момент меняет спор или подтверждение клиента, пропускаются через `FOR UPDATE SKIP LOCKED`, закрываются на следующем проходе, если условия ещё верны). Проверено: гонки подтверждения и автозакрытия дают один результат, спор держит строку, закрытую сделку с открытым спором получить нельзя.

**Защита order-notify-worker.** Проверка JWT отключена (`--no-verify-jwt`), потому что вызов защищён секретом `NOTIFY_WORKER_SECRET`: нет или короче 32 символов → 503 (обработчик не запускается); нет заголовка `x-worker-secret` или он неверный → 401; секрет не попадает в ответы, журнал, клиентский код и таблицы. Служебные функции очереди и серверных задач закрыты от анонимов и обычных пользователей (тесты).

**Порядок выпуска.** После шагов файла 57: запустить `migration_58_deadlines.sql` (одним запросом), затем выполнить `supabase/deadlines_schedule.sql`, потом публиковать сайт. Без расписания сроки и задачи по изменению заказа (оплата, статус, срок) всё равно обновляются триггером, но просрочка «по часам», напоминания и автозакрытие обмена не наступят.

**Ограничения.** Часовой пояс кабинета по умолчанию Asia/Bishkek — это допущение, владельцу нужно проверить. Задачи по времени появляются с задержкой до 10 минут. Напоминания только в Telegram и только подписчикам заказа. Срок оплаты и интервал доставки вводятся вручную: автоматического расчёта нет. Правила дублей — как у очереди (файл 57).

Проверка на временной базе (входит в `bash tests/run_db_tests.sh`): `bash tests/deadlines_test.sh` — 15 сценариев (заказ без срока, границы и пояса, повторный и параллельный запуск, частичная и полная оплата, перенос срока, отмена и приостановка, выключение и отзыв подписки, оплата между постановкой и отправкой, частота и часы, права и изоляция, пульс, автозакрытие обмена и гонки со спором).

## Главное правило: старые файлы не запускать

Несколько файлов переписывают одни и те же функции. Например, `get_client_order`, страница клиента, есть в файлах 0, 1, 4, 5, 7, 11 и 12.
Если запустить старый файл 07 после 12, клиенты перестанут видеть историю заказа.

Поэтому в начале каждого файла стоит **защита**: если в базе уже отмечен файл с бо́льшим номером, запуск
останавливается с сообщением `СТОП: файл N старше уже запущенных…`. **В базе при этом ничего не меняется.**

- Последний файл можно запускать повторно, это безопасно.
- Увидели «СТОП» — значит, этот файл уже не нужен.

## Как добавить новое изменение базы

1. Создать файл со следующим номером: `migration_27_что_делает.sql`.
2. В начало вставить защиту, а в конец — отметку. Скопировать оба блока из любого файла и поменять номер на новый.
3. Проверить на компьютере: `bash tests/run_db_tests.sh`. Должно быть «🎉 Все проверки пройдены».
4. Запустить файл в Supabase → SQL Editor → Run.
5. Если меняется функция, которая уже есть в старых файлах, копировать её **из самого нового файла**.

## Проверки перед публикацией

`bash tests/run_db_tests.sh` (нужен Docker Desktop). Скрипт создаёт временную пустую базу, применяет все файлы по порядку
и проверяет:

1. байеры не видят и не меняют чужие заказы, поставщиков и переписку с поддержкой;
2. админ видит любой кабинет, но изменить его не может;
3. без входа таблицы закрыты;
4. клиент по ссылке видит свой заказ, а цены поставщика, курсов, себестоимости, прибыли и внутренних заметок не видит;
5. отключённая или заменённая ссылка клиента больше не работает;
6. фото заказа видит только свой кабинет;
7. все файлы отмечены в `schema_migrations`;
8. старый файл не запускается поверх новых.

Рабочую базу скрипт не трогает.

## Как восстановить базу с нуля (новый проект Supabase)

1. Создать новый проект на supabase.com.
2. SQL Editor: по очереди запустить `supabase_schema.sql`, потом `migration_01…`, `migration_02…` и так далее до последнего.
3. После `supabase_schema.sql` и **до** `migration_02…` сделать себя админом:
   зарегистрироваться на сайте, затем в SQL Editor выполнить
   `insert into public.admins (user_id) select id from auth.users where email = 'ваша@почта';`
4. Authentication → Sign In / Providers: включить регистрацию по почте и, если нужно, Google.
   Authentication → URL Configuration → Site URL: адрес сайта.
5. Edge Functions: создать все пять: `ai-assistant`, `photo-orders`, `telegram-notify`, `push-notify`, `order-notify-worker` (код в `supabase/functions/…`).
   В Secrets добавить `GEMINI_API_KEY` и `TELEGRAM_BOT_TOKEN`.
6. В `config.js` вписать новый Project URL и publishable-ключ.

## Ежедневная работа (файл 59)

**Простой режим в профиле.** `profiles.ui_simple` и `ui_simple_explicit`; функции `my_ui_prefs()` и `my_ui_prefs_set()`. Автоматический выбор по числу заказов (меньше 15) заполняет только пустой профиль и помечается как неявный; явный выбор человека никогда не перезаписывается и действует на всех устройствах. Локальная копия в браузере остаётся запасной (если файл 59 не запущен).

**Модули «Магазин» и «Обмен».** `workspaces.module_shop` и `module_exchange` (по умолчанию включены), меняет только владелец (`ws_daily_set_modules`), читают участники (`ws_daily_get`). Отключение только скрывает пункты меню: данные, действующие сделки, споры, автозакрытие обмена и финансовые правила не меняются. Пункт «Обмен» остаётся в меню (в том числе в простом режиме), пока есть сделки в статусах new/paid/confirmed/sent или открытый спор.

**Часовой пояс.** Моменты оплаты и доставки хранятся как точные моменты (timestamptz) и **не сдвигаются** при смене пояса: меняется только то, как они показываются, и границы дат; `ws_timezone_preview` заранее показывает, у скольких заказов изменится дата. Владелец подтверждает пояс (`ws_confirm_timezone`) или меняет (`ws_set_timezone`); каждая смена пишется в `ws_timezone_log`. Пока пояс не подтверждён, в Настройках стоит предупреждение. Значение пояса одно: экраны «Часовой пояс» и «Напоминания» обновляются без перезагрузки.

**Клиент по постоянному номеру.** Форма заказа выбирает клиента из списка по `client_id` (поиск по имени, телефону, Telegram; клиенты без адреса находятся; одинаковые имена различаются последним заказом). Сопоставление по имени или окончанию телефона не возвращено. Триггер отказывает (`bad_client`), если клиент из другого кабинета; у уже существующих заказов с таким несоответствием можно править другие поля (проверка `scripts/diagnose_supabase_readonly.sql`, строка 26).

**Права.** Помощник не может менять модули, пояс и правила напоминаний: сервер отвечает `forbidden`, скрытая кнопка проверку не заменяет.

**Порядок выпуска.** После файла 58 запустить `migration_59_daily_work.sql` одним запросом, затем публиковать сайт. Расписаний файл не добавляет.
